01소개

“시스템이 위험을 알아차리는 시점을
얼마나 앞당길 수 있는가”

백엔드를 공부하며 붙잡아온 질문

동국대학교 정보통신공학과에서 백엔드 개발을 공부하고 있습니다. 물으면 답하는 시스템, 스스로 감시하는 시스템, 터지기 전에 아는 시스템은 각각 다른 설계를 요구했습니다. 세 개의 프로젝트에서 같은 질문을 세 번 다르게 풀며, 위험을 알아차리는 시점을 즉시에서 상시로, 상시에서 사전으로 앞당겨 왔습니다.

기술은 필요를 겪은 뒤에 넣습니다. 콜드체인 관제 시스템에서는 5,000대 부하로 병목을 직접 확인한 뒤에야 Kafka와 TimescaleDB로 전환했고, 예측 모델도 "정확하다"고 주장하는 대신 통제된 벤치로 트레이드오프를 측정해 기본값을 정했습니다.

다만 지금까지 제 시스템의 사용자는 시뮬레이터와 팀원이었습니다. 실제 트래픽과 실제 장애가 흐르는 환경에서, 만들 줄 아는 개발자에서 운영되는 서비스를 책임질 줄 아는 개발자로 한 걸음 더 나아가는 것이 다음 목표입니다.

전공 동국대학교 정보통신공학과
관심 영역 이상 탐지 · 관측 가능성 · 데이터 파이프라인
작업 방식 병목은 측정하고, 설계 판단은 근거를 남긴다
  1. 즉시 Fremen

    “모든 요청을 AI에 태우지 않고도 즉시 판별할 수 있는가”

    룰 기반 1차 필터로 안전한 문자는 AI 호출 없이 0.01초대에 판별하고, 의심 문자만 비동기로 AI 서버에 넘기는 연동 계약을 설계했습니다. AI를 쓰는 서비스일수록 AI를 거치지 않는 경로가 성능을 결정한다는 것을 배웠습니다.
  2. 상시 K8s 모니터링

    “요청을 기다리지 않고 시스템이 스스로 감시하게 할 수 있는가”

    Kubernetes API·Prometheus·Loki라는 성격이 다른 세 소스를 주기 수집하는 모듈로 탐지 파이프라인의 입구를 만들고, EKS 위에 GitOps 기반 CI/CD를 구축했습니다. 감시하는 시스템은 그 자신이 가장 먼저 살아 있어야 했습니다.
  3. 사전 coldchain

    “터지기 전에 알 수 있는가”

    통계 탐지로 급변과 점진 이탈을 구분한 뒤, 온도 추세로 임계 도달 시각을 계산해 이탈 전에 경고를 보냈습니다. 가장 오래 고민한 것은 예측이 맞았을 때가 아니라 틀렸을 때의 설계였습니다.

Fremen

모든 요청을 AI에 태우지 않는 스미싱 탐지 백엔드

문자를 룰 기반으로 1차 판별하고, 의심 건만 AI 서버로 넘겨 3단계 위험 등급과 근거 문장으로 돌려주는 Android 스미싱 탐지 서비스. 팀 프로젝트에서 백엔드를 담당했습니다.

  • 모든 문자를 AI 서버로 보내면 비용과 지연이 감당되지 않는 문제 — 룰 기반 1차 필터로 안전한 문자는 AI 호출 없이 0.01초대에 판별하고, URL·숫자가 포함된 의심 문자만 넘기는 연동 계약 설계
  • LLM 응답을 기다리는 동안 서버가 묶이는 지연을 WebClient 비동기 호출로 요청과 저장을 분리해 해결
  • 모바일 앱 연동 검증을 위해 AWS EC2 배포, 프론트·AI 파트와 API 명세를 먼저 합의하는 병렬 개발 방식 정착
